# USDC 双向 Maker 等比网格

策略文件：[`backend/strategies/usdc_hedge_grid.py`](../backend/strategies/usdc_hedge_grid.py)，策略 ID `usdc_hedge_grid`，版本 `1.0.0`，执行模型 `maker_grid_v1`，协议/引擎 `1.2.0`。

**当前支持历史回测和持续模拟，正式实盘运行尚未接入。** 本次没有使用真实交易凭据，也没有完成真实账户 Hedge / GTX / 条件止损验收。现有 Binance 适配器不具备这套网格所需的完整真实委托与对账链路；应用继续阻断实盘启动，不能靠设置 `MK_ENABLE_LIVE=1` 启用。

## 市场、账户与参数

可从 `BTCUSDC`、`ETHUSDC`、`SOLUSDC`、`BNBUSDC`、`XRPUSDC` 中选择任意非空子集，既可以只选一个，也可以五个一起运行。一个账户仍只运行一个策略实例；所有币种共享账户资金，行情按共同完成的时间戳对齐。策略声明 `symbols.mode="any"` 且 `values` 是允许列表，不接受其他交易对。

要求合约 `futures`、双向持仓 `hedge`、全仓 `cross`，声明杠杆范围 1–5 倍、最低资金 1,000 U。持续模拟取声明的最小杠杆，即 1 倍；回测可在范围内选择杠杆。界面默认初始资金为 10,000 U，默认每格名义金额为 100 U；最低资金不意味着任何参数组合都能挂满全部网格。现货、单向和逐仓不能用于此模型。

| 参数 | 默认值 | 范围 | 含义 |
| --- | --- | --- | --- |
| `grid_spacing_pct` | 0.6 | 0.05–20 | 每格百分比间距，公比 `q = 1 + grid_spacing_pct / 100`。 |
| `levels_per_side` | 4 | 1–12，整数 | 每币种每方向的候选网格层数。 |
| `order_notional_u` | 100 | 5–100,000 | 单格名义金额 U，不是保证金；原始数量为金额除以网格价。 |
| `take_profit_steps` | 1 | 1–20，整数 | 相对该格入场价的止盈距离，单位为格。 |
| `stop_loss_steps` | 4 | 1–100，整数 | 相对该格入场价的止损触发距离，单位为格。 |
| `stop_limit_offset_bps` | 2 | 0.1–100 | 止损触发价外的被动限价偏移；1 bps = 0.01%。 |
| `max_lots_per_side` | 4 | 1–24，整数 | 每币每方向的未平 lot 与未成交入场单总数上限。 |
| `max_margin_pct` | 50 | 1–90 | 总权益用于持仓和入场挂单保证金的策略预算百分比，各币均分。 |

跨参数还要求 `stop_limit_offset_bps / 10000 < 1 - (1 + grid_spacing_pct / 100)^(-stop_loss_steps)`，保证被动止损限价仍处于该格入场价的亏损一侧。不满足时策略明确报错，在生成委托前终止；仅通过各参数独立范围校验不代表这个组合有效。执行器还会先按 tick 量化所有保护价，量化后方向错误或止损限价跨回入场价会拒绝入场。

回测 `fee_rate` 按 Maker 费率解释，默认估计为 `0.0002`（0.02%）；可编辑，或从有凭据的账户读取相应费率。持续模拟采用明确标记的固定 Maker 费用假设。`slippage_bps` 必须为 0，因为模型按限价撮合；这不代表真实市场没有流动性、排队或机会成本。

## 锚点、价格与资金分配

每个币种独立以本次策略实例第一次收到的完整 K 线收盘价为固定锚点 `A`。锚点保存在策略状态中，普通重启恢复同一锚点；它不会随每根行情滚动，也不自动追价重置。训练、验证各用全新策略和账户，因此分别建立锚点。

第 `i` 层（从 1 开始）的原始目标价格如下，随后由框架按交易对规则量化：

| 项目 | LONG 多头 | SHORT 空头 |
| --- | --- | --- |
| 入场价 `P` | `A / q^i`，`buy + LONG` | `A × q^i`，`sell + SHORT` |
| 止盈限价 | `P × q^take_profit_steps` | `P / q^take_profit_steps` |
| 止损触发价 `S` | `P / q^stop_loss_steps` | `P × q^stop_loss_steps` |
| 止损限价 | `S × (1 + offset_bps/10000)`，卖出 | `S × (1 - offset_bps/10000)`，买入 |

入场不使用市价初始化。只有多头入场价低于当前收盘价、空头入场价高于当前收盘价时才尝试挂单；价格已越过某格时等待其回到可被动挂单的一侧。相同币种、方向、层级有未平 lot 或入场单时不重复下单；该格完全退出后允许以新的周期 ID 补回。

总保证金预算是 `equity × max_margin_pct / 100`，再除以所选币种数量得到每币预算，分别扣除该币已有双腿持仓和入场单占用。候选顺序按层级交替 LONG、SHORT，使有限预算先覆盖两侧；不同币种不能吞掉其他币种的预留份额。极小预算、不同交易规则或既有敞口仍可能使某币/某侧无法挂单，不保证任何资金量下都对称挂满。

策略每个候选单估算 `名义金额 / 杠杆 + 名义金额 × 1%`，后者是保守预留，**不是实际费率**。执行器另外按量化后的真实模型数量、限价及 Maker 费率核验资金，并在挂单存在时预留保证金与费用。多空腿保证金相加，不净额抵消；界面分别显示持仓保证金和入场挂单预留。默认五币、每币四层双向共有 40 个候选入场单，挂满与否取决于权益、杠杆及交易规则。

超过预算、权益非正或发现未受完整保护的 lot 时，策略撤销入场单并停止补仓，保留已有退出单。它不会为了满足预算自动以市价减仓。每币精度、最小数量和最小名义金额来自实验绑定的交易所规则快照或持续模拟行情规则；不在策略源码中硬编码当前 tick、step、最小金额或交易所订单容量。数量向下取整后仍可能低于最小金额，执行器会拒绝而不是擅自增大风险。

保证金预算按已收盘行情估值检查，不是盘中硬上限；价格跳变可能使已有持仓超预算。估值下降或退出释放预算后，允许重新补充网格。

## 订单与 K 线撮合时序

入场和止盈都是 `LIMIT + GTX`；止盈是预先挂出的普通限价单，不等待新的止盈触发事件。止损是框架内部 `STOP_LIMIT + GTX`：条件满足后尝试挂被动限价，不包含 Taker 回退。

1. 每根共同完成的 K 线先处理已有委托，再按收盘价估值并调用策略。
2. 策略在本根收盘后提交的入场单最早下一根有效。买单只有 `low < price`、卖单只有 `high > price`，且该根成交量大于 0，才按限价全量成交；刚好触价或零成交量都不算成交。
3. 入场成交时，执行器同步创建关联 lot、该实际模拟成交数量的 TP 和 SL；不等待下次策略回调。两张保护单最早下一根 K 线有效，不能利用入场当根未知的价格先后制造盈利退出。
4. 卖出止损在 `low <= stop_price` 时触发，买入止损在 `high >= stop_price` 时触发。触发时分别以 `min(open, stop_price)`、`max(open, stop_price)` 检查 GTX；会立即成交的限价被拒绝。
5. 通过检查的止损在触发当根只变成挂单，最早再下一根严格穿价才成交。同根止盈/止损顺序不明时，先处理止损并抑制该 lot 的当根盈利退出，不假定先止盈。
6. 一个 lot 全部退出后取消该 lot 其余兄弟退出单；部分手动减仓按剩余数量缩减保护。另一 lot 或相反方向的持仓不会被这一退出意图消耗。止损触发或被拒本身不撤止盈；止盈在后续 K 线仍可能成交，但不代表止损已经完成。

这里的“全量成交”是 OHLC 模型假设：没有真实买卖盘口、排队优先级、可成交量分配或部分成交模拟。零成交量只阻止成交，不阻止模型观察止损触发；记录 `ZERO_VOLUME_FILL_SKIPPED` 说明穿价却未成交。`GTX` 检查基于参考价，不能还原交易所撮合。模型保存 `liquidity="simulated_maker"` 及完整 `assumptions`；严格穿价和止损优先只是明确的保守处理规则，不是收益下界保证。回测结束保留未平 lot 与未成交单，不人为平仓。

**Maker 止损不能保证退出。** 例如多头下跌触发止损后，卖出限价仍可能留在市场上方长期未成交；把卖价改到可立即成交的一侧又可能违反 GTX 被拒。`stop_triggered` 只表示已触发，`stop_rejected` / `unprotected` 表示保护异常；这些状态都不意味着已止损。框架继续展示持仓、浮亏和风险，并停止新增敞口；不会暗中切换市价。限价不保证成交、Post Only 避免立即吃单的性质见 [Binance 订单类型说明](https://www.binance.com/en/support/faq/detail/360033779452)。

## 暂停、平仓、恢复与持久状态

| 操作或情况 | 当前模拟行为 |
| --- | --- |
| 停止开仓 | 撤未成交入场单，保留 lot 和 TP/SL，继续使用新鲜行情管理保护。 |
| 策略异常 / 保护缺失或拒绝 | 锁存错误并暂停新增风险；已有 lot 和仍有效的退出单继续管理，不伪装为空仓停止。 |
| 行情缺失、过期 | 撤入场，保留已有 lot / 退出单；不使用旧价补成交，显示等待行情。 |
| 行情断档 | 不补发过期开仓；仅处理当前完整 K 线，记录缺失期间的成交/触发顺序无法重建。 |
| 平仓并停止 | 撤入场；有新鲜参考价时，将原退出单替换为参考价外一个 tick 的逐 lot `LIMIT GTX` 退出单。缺少参考价时保留原保护并等待。 |
| 平仓单未成交 | 执行端保持 `flattening`、命令保持 `running`，仍显示残余仓位；可能长期无法完成。重复处理不重复挂同一退出单。 |
| 平仓完成 | 无未平 lot 且无挂单后，执行端才确认 `stopped` 并完成命令。 |
| 恢复运行 | 解除停止新增风险/flattening 控制，恢复策略检查；保护仍异常时会再次暂停。 |
| 修改策略或参数 | 需执行端确认停止并清空 lot / 挂单；禁止用新配置覆盖仍有风险的订单簿。 |

“平仓并停止”是被动退出请求，不是保证即时撤离风险的紧急市价平仓。替换后的 flatten 单按其挂单价格等待，不持续追价；原 TP/SL 已被该操作替换。

模拟订单生命周期、成交、lot、关联保护、资金预留、完整事件、策略锚点/周期、停止标记和事件游标一起持久恢复。相同 `client_order_id` 的相同意图不重复创建，不同意图被拒绝；同一根已处理 K 线不会重复成交。独立账户进程在有效租约和 fence 下事务提交订单、成交及快照；关闭页面或单独重启 API 不负责终止该进程。生产级故障注入与真实交易所幂等仍属于 [验收清单](ACCEPTANCE.md)。

账户已确认停止且无持仓、挂单或待执行意图时，可以切换执行模型。转换保留余额、手续费、成交和收益曲线，原执行快照归档并记录审计；新的执行代号隔离策略重新使用的客户订单号。每日、每月收益按北京时间边界统计。相同 K 线且配置、行情新鲜度和指令均未变化时只更新心跳；历史快照仍会随成交和事件累计增长，长期容量需持续监测。

## Binance 官方边界与后续接入

以下为 2026-11-03 的官方资料核对，证明当前接口设计与产品能力范围，**不是五个交易对在某个真实账户上的验收记录**。

- USDⓈ-M 持仓模式接口将 Hedge / One-way 定义为全币种设置；官方功能说明同时列出 USDT/USDC 合约和 Hedge。结合本次公开 `exchangeInfo` 中五个交易对均为可交易 USDC 永续，可按当前官方设计接入双向；没有据此确认任何特定账户权限或地区资格。[持仓模式接口](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade#change-position-mode-trade)、[USDC 与 Hedge 功能说明](https://www.binance.com/en/support/faq/detail/1f02faf97a6f4a418121514aa9dd7976)、[公开交易规则](https://fapi.binance.com/fapi/v1/exchangeInfo)。
- 普通入场/止盈将映射 `POST /fapi/v1/order` 的 `LIMIT/GTX`；条件止损须映射 `POST /fapi/v1/algoOrder` 的 `CONDITIONAL/STOP/GTX`。Hedge 必须指定 `positionSide`，不能发送框架内部的 `reduce_only` 为 API `reduceOnly`；固定数量逐格退出也不能用平整腿的 `closePosition` 代替。[官方下单与 Algo 参数](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade)。
- Binance 网页已有 OTOCO/OTO TP/SL 功能；本次核对的公开 USDⓈ-M 创建接口未提供等价的原子组合下单契约。因此框架的独立 TP/SL 必须自行关联、撤销兄弟单，并处理部分成交及撤单竞态，不能声称已使用交易所原生 OCO。[官方 TP/SL 说明](https://www.binance.com/en/support/faq/detail/e1ee1738141c49718550fa9061be4bf3)。

当前真实适配器的 `submit_order` 仅覆盖普通 `MARKET` 和 `LIMIT GTC`，尚未接上 GTX、Algo 创建/撤销/查询、成交事件流及逐 lot 兄弟单协调。将来实际接入时，交易所同币种 LONG / SHORT 各自是聚合持仓；框架 lot 是内部成本和数量分配记录，不能声称交易所保存了每格独立仓位。需要按实际成交增量建立保护、去重成交事件、序列化同方向退出、核对剩余仓位，并处理成交后保护创建失败及断线恢复。不能把本地模拟中的同步创建误写成远端 API 原子事务。

真实规则和限额必须在接入时重新获取并做拒单处理，包括价格/数量精度、名义金额、动态价格带、普通/条件单数量和频率限制；不同订单类别不能共用一个固定容量常量。条件单已迁移至 Algo 路径，详见 [Binance USDⓈ-M 变更记录](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/change-log#2025-11-06) 与 [交易参数](https://www.binance.com/en/futures/trading-parameters)。正式实盘的事件对账、运行授权、强制单执行者、资金费/强平和真实账户验收完成前，继续保持实盘闸门关闭。

```bash
.venv/bin/python -m pytest -q tests/test_grid_strategy.py tests/test_maker_engine.py tests/test_engine.py
```
